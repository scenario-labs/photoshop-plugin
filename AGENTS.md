# AGENTS.md

How to build, test and change this repository. Read [docs/spec/SPEC.md](docs/spec/SPEC.md) section 2 (architecture, link and pairing) and [docs/spec/MCP.md](docs/spec/MCP.md) before changing the link or the tools.

Claims here are marked *verified live* (in Photoshop), *tested automated* (Node, no Photoshop) or *not tested*.

## Commands

```sh
npm ci                 # installs ws, the helper's only run-time dependency
npm test               # all unit and integration tests, about 15 s
node test/run.js setup # only the test files whose path contains "setup"
npm run lint           # node --check, JSON, no em dashes, no machine paths or addresses, UXP rules
npm run build          # plugin/dist/main.js (release bundle)
npm run build:dev      # development bundle (adds the dev token import, below)
npm run package        # build/scenario-photoshop-0.6.0.ccx
npm run package:dev    # build/scenario-photoshop-0.6.0-dev.ccx
```

`npm test` and `npm run lint` pass on Node 20 and 22 on macOS (*tested automated*). CI runs them on Node 20 and 22, on Ubuntu and macOS.

## Rules for code

- **Plugin code is plain JavaScript** with no dependency. The bundler wraps each file in its own function scope and resolves relative `require`s at build time; `uxp`, `photoshop`, `os` and `fs` go to UXP's own `require`. No `eval`, no `new Function`, no top-level declaration named like a UXP global (a top-level `const URL` breaks UXP's WebSocket, *verified live* on 27.11 with a probe plugin). `npm run lint` checks this.
- **Everything the plugin reads from UXP or Photoshop goes through `plugin/src/host.js`**, so the rest runs under Node with a fake host.
- **The link protocol lives in `shared/protocol.json`** and is implemented twice, in `plugin/src/bridge/protocol.js` (pure JavaScript) and `helper/src/link/crypto.js` (`node:crypto`). Change both and `test/vectors/pairing.json` together; `test/unit/pairing-proofs.test.js` checks they agree byte for byte.
- **The pairing token is never logged, printed, put on a command line or sent over the socket.** Tests generate tokens; none is stored in the repository.
- **Tool errors are one line, `Type: message`**, with a type from `shared/errors.json`.
- **Scenario keys** (SPEC 2.10, Credentials): the key and secret go only to `base_url` in `shared/scenario-api.json`, as HTTP Basic, with `redirect: "error"`; `client.request` takes relative paths only. A redactor removes the exact key, secret and Basic value from log lines, error texts, copied text and diagnostics. Secure storage entry names are not encrypted, so a key is stored under `scenario.key.` plus a SHA-256 prefix of the key, and the index `scenario.accounts` holds the project name and id, the hash and the last 4 characters. Of the project listing, only the project name and id and the key's own role and scope are kept: it also lists members' emails and every key id. `test/unit/secret-leak.test.js` checks all of this on the release bundle; tests use random keys against `test/helpers/mock-scenario.js`, never a real key.
- **Price checks and spending**: the dry-run flag appears once in the plugin, as `DRY_RUN_QUERY` in `plugin/src/scenario/dry-run.js`; other modules derive its name from that object. `client.request` lets a `POST` to `/generate` through only as a price check carrying that exact object, or as the paid request carrying the frozen `PAID_REQUEST` marker of `plugin/src/scenario/paid.js` (compared by identity) and no query at all; everything else is refused before it is sent (`beforeSend`). `paid.js` also refuses a body holding the flag's name. `test/unit/price-checks.test.js` checks that the flag appears nowhere else in `plugin/src` or `shared`, exactly once in the bundle, and that every price check the mock received had the query string `?dryRun=true`; `test/unit/paid-call.test.js` checks every answer of the paid request and that it never carries the flag. A price check answered with a job id raises an alarm that stops all price checks until the plugin restarts. Rules that depend on the model (which inputs change the price, stand-ins, lane defaults) live in `shared/catalog-map.json` as data, from the measurements in `test/fixtures/m2.0/`.
- **Paid generation** (SPEC 6.1, 6.2, 6.4): `jobs/runner.js` refuses at once in no-spend mode or during a 429 pause; checks idempotency (the quote id is the key: a known key replays its job, the same key with another request is `IdempotencyConflict`, a matching request uploading, awaiting approval, being sent or Unknown is `RequestInFlight`), then the quote (single use, 120 s, same fingerprint); writes the ledger record before anything is sent (a record that cannot be written sends nothing); uploads references and prices again with the real asset ids (a different price waits in `awaiting_approval`); sends once with a 60 s timeout and never retries. Answers are classified in `paid.js`; any status the table does not name reads as Unknown, the reading that never loses a paid result. Only the person resolves an Unknown job. `test/unit/generate-panel.test.js`, `test/unit/m3-jobs.test.js` and `test/unit/bundle-m3.test.js` cover this.
- **Results and placement**: downloads take a fresh signed link per attempt (kept in memory only), check its host and the final host after redirects against `shared/scenario-api.json` `downloads.origins`, send no key, write `<file>.part` and rename it. `host.placeResults` runs a plan from `apply/plan.js` in one `executeAsModal` scope and one suspended History state, rolled back if anything fails. A result lands by itself only for the person's own job, in the same Photoshop session, when its document is the active one; never after a restart. A Remove BG job whose source was the Background finds the Background of its reopened document even when Photoshop gave it a new layer id.
- **Edit and Enhance** (SPEC 3.8, 5.8, 9.3): the lanes are built from `lanes/` and run through `lanes/flow.js`, which builds the request again at the click, takes the capture and hands it to the runner, so the money contract above applies unchanged. A check after placement only adds badges or notes; it never removes a placed take or the saved file, and **Changed outside** offers Undo. A capture that must shrink to fit the upload limit carries `reduced` (Edit shows Input reduced); for models whose output follows the input (Upscale, Remove BG) it stops with `InputReduced` before anything is sent, and the caller prices again with `read_long`. `test/unit/m4-*.test.js` cover this on the fake Photoshop in scene mode.
- **Jobs and restarts** (SPEC 6.3, 6.4): the ledger is the source of truth. `ledger.load()` applies the restart transitions before anything else runs (submitting to Unknown; uploading and awaiting approval to not sent; applying to ready, to be checked for a placed layer first; running jobs keep their state and resume) and logs each as `jobs: restart: <first 8 characters of the id> <before> -> <after>`. `runner.recover()` runs after the accounts load: a job whose saved file is missing goes back to `download_failed`, a job recovered from placing becomes `applied` if a layer with its asset id is in an open document, and the rest resume under their own project only (the record keeps a hash of the project id). Unknown resolution (`resolve.js`) uses the job id when the record has one, else lists the project's jobs from 10 minutes before the claim to 60 minutes after it, newest first, page by page, and matches the model and every recorded parameter, the prompt read back from its text asset; one exact match is preselected; **Mark not sent** needs a complete look-up less than 10 minutes old with no exact match. Placement goes to the job's own document: the same id in the same session, else the same saved file (`document_key`, a hash of its path), else for older records the same title and size; a closed or background document holds the job (`DocumentClosed`, `DocumentNotActive`). A status read refused for the key keeps polling at the normal pace; the job is never given up. The panel draws `view-model.js`; it does not decide states or actions. `test/unit/m5-*.test.js` cover this.
- **Test hooks** (`plugin/src/dev/test-hooks.js`, development builds and Node tests only): a point in the job flow can be armed to hold, delay or fail once (`upload`, `price_after_upload`, `paid_answer`, `poll`, `download_part`, `place`). They live in memory, so a restart disarms them. Release bundles carry a stub whose points do nothing; `test/unit/bundle.test.js` and `test/unit/m5-jobs.test.js` check it.
- **No Scenario call at launch**: the catalog and price checks start when the panel is shown (the `show` entrypoint), when the person uses the panel, or when an agent calls a tool. `test/unit/creation-panel.test.js` and `test/unit/bundle-m2.test.js` check this. The one exception is SPEC 6.4: jobs that were running or downloading when Photoshop closed resume at launch, so a paid result is not left waiting; with no such job, launch calls nothing.
- **Scenario errors**: bodies carry `reason` or `message`, no code (measured live). Classify by HTTP status plus the known texts in `shared/scenario-api.json` (an unknown key answers 403 "Given APIKey does not exists"), and show Scenario's own text otherwise. Panel texts for each sign-in state are in `plugin/src/ui/account-view.js`, worded as SPEC 3.13.
- **Client sessions** (SPEC 2.6): the owner gives each client a 16-byte session id when it connects and new ids to every client each time a plugin link opens; a name is set once, at the first `initialize`, cut to 64 characters. Calls carry only the session; the plugin takes names from the `clients` list and refuses a session it does not list. When a session leaves the list or the link drops, the plugin ends what was granted to it (in this build, the spending allowance). `test/unit/owner-checks.test.js` and `test/unit/plugin-link.test.js` cover this.
- **Dependencies**: MIT-compatible only, pinned to exact versions, listed in `THIRD_PARTY_NOTICES.md`; change `package-lock.json` and `helper/npm-shrinkwrap.json` together. Workflows pin each action by full commit and declare least permissions. `test/unit/supply-chain.test.js` checks all of this.
- The helper's tool list comes from `shared/catalog.json`. A test caps `tools/list` at 40,000 characters and each description at 2,500.
- Public repository: no machine paths, personal or customer names, email addresses, internal decision numbers or secrets. No em dashes in docs or comments. `npm run lint` checks what it can; maintainers can add a private word list with `LINT_DENYLIST=<file>`.

## Try the link in Photoshop (development)

*Verified live* on Photoshop 27.11 (macOS) with this build: the dev token is adopted and its file removed, `scenario_status` comes back from the live Photoshop through the helper, and the random source is `getRandomValues`. The plugin's WebSocket sent `Host: localhost:9890`, `Origin: file://` and `User-Agent: WebSocket++/0.8.2`. The panel's look and 26.x were not checked.

1. `npm run package:dev`.
2. Install the package with Adobe's installer (macOS path shown; the plugin loads at the next Photoshop launch). The installer needs an absolute path: a relative one fails with status -160 (*verified live* on 27.11).
   ```sh
   "/Library/Application Support/Adobe/Adobe Desktop Common/RemoteComponents/UPI/UnifiedPluginInstallerAgent/UnifiedPluginInstallerAgent.app/Contents/MacOS/UnifiedPluginInstallerAgent" --install "$PWD/build/scenario-photoshop-0.6.0-dev.ccx"
   ```
   Installing a newer version over an older one (0.2.0-dev over 0.1.0-dev) reported success and kept the data folder and secure storage; the new version loaded after a Photoshop restart (*verified live* on 27.11). When the same version is already installed, the installer reports success but keeps the old copy; `--remove Scenario` removes it, and also clears the plugin's data folder and secure storage (saved keys, the pairing token and the job records), so the person signs in again. Bump the version instead when keys should stay.
3. `node test/live/m1-live-check.js`, then start or restart Photoshop. The script writes a fresh token as `dev-pairing-token` into the plugin's data folder; a development build adopts it at startup and deletes the file, so no one has to open the panel. The script then runs the helper with that token and calls `scenario_status` until Photoshop answers. It prints the status (document titles hidden unless `--show-titles`) and the `Host`, `Origin` and `User-Agent` the plugin's WebSocket sent.

To sign a development build in without the panel, put a file `dev-api-key` in the same data folder before the restart, readable by you only (`chmod 600`), with two lines `SCENARIO_API_KEY=...` and `SCENARIO_API_SECRET=...`. At startup the build runs the panel's own Save and test with that pair, stores it in secure storage only if Scenario accepts it, and deletes the file in every case. The log says only `dev build: API key imported` or the error type, never the values.

Release builds replace both dev imports (pairing token and API key) with empty stubs; `test/unit/bundle.test.js` checks that the release bundle contains neither.

## Check prices from an agent client (development)

`node test/live/m2-live-check.js` runs the M2 exit check from a live Photoshop. Like the link check above, it writes a fresh `dev-pairing-token` (run it before installing or restarting), starts the helper with `SCENARIO_NO_SPEND=1` and waits for the plugin. It then needs the panel signed in: if `scenario_status` reports `signed_in: false`, it stops and changes nothing. Signed in, it calls `list_models` for three lanes and `estimate_cost` for the Image default (GPT Image 2.5 Flare, low, 1024 x 1024, 1 take; recorded at 2 CU), the Edit default with a mask (2 takes; 3 CU) and Remove BG (851 Labs; 1 CU), and prints each price. The script never contacts Scenario itself: the price checks go through the plugin and its one dry-run constant. The 851 Labs check uploads one blank 256 x 256 image to the project, hidden from the Library.

*Verified live* on 27.11 with the 0.3.1 development build, signed in through `dev-api-key`: `list_models` answered for the three lanes, and the three prices came back exact at 2, 3 and 1 CU, as recorded. The script needs one Photoshop restart to adopt its token, so it can also serve as the restart that imports `dev-api-key`.

## Run a creation flow (development)

*Not tested* live yet as a whole; the placement steps were *verified live* separately with a probe plugin and the development entry. One Create image take with the default spends 2 CU.

1. Install the development package as above and restart Photoshop; the panel stays signed in (keys live in secure storage). A first install can be signed in with `dev-api-key`, see above.
2. Leave no document open (Create image opens its result as a new document), or open one and select a layer or make a selection: the context card names what the action works on and where the result lands.
3. Open **Plugins > Scenario**. Click an action chip and type the prompt. The button reads `Create image · 2 CU` for one take of GPT Image 2.5 Flare at low quality (Takes chip set to 1 take); an empty prompt reads `Fill in the prompt to see the price`.
4. Click the button. The context card shows "Sending to Scenario", "Queued on Scenario", "Generating" with a progress bar, "Downloading" and "Placing in the document", then the Takes card shows the result and the price words "quoted 2, charged 2 CU".
5. Check the layers: one take is a layer `Scenario <kind> <first prompt words> <last 6 characters of the asset id>`; several are a group `Scenario <kind> <first prompt words> (<n> takes)` holding `Take <i> <tail>`, take 1 visible; an edit is masked to the selection. One History state ("Scenario: Place image", "Place edit", "Expand", "Place upscale" or "Place cutout"), the person's previous active layer active again, and each layer's XMP (`scenario:schema="1"`, `assetId`, `jobId`, `modelId`, `prompt`, `cuQuoted`, `cuCharged`). The files are in the data folder under `Scenario/<kind>/<YYYYMMDD>/`, the job record under `jobs/`.

## Run the Edit and Enhance paths live (development)

The panel offers these as actions. For scripted checks, a development build also runs each route from a request file: `plugin/src/dev/live-run.js` checks the data folder every 2 s for `dev-live-run.json`, removes it when read, makes a document of its own from a fixture PNG in the data folder, sets the selection (rectangle or ellipse, with a feather), prices the run through `lanes/flow.js`, and with `"spend": true` generates when the price is at most `max_cu`. It waits for the result to land and the checks to run, saves the composites before and after, writes `dev-live/<id>/result.json` (the view, the request, the quote, the price charged, the capture sizes, the placement badges and notes), and closes the documents it made without saving. It never reads or changes a document it did not make. Release bundles carry a stub; `test/unit/bundle.test.js` checks the release bundle has none of it, and `test/unit/m4-dev-live.test.js` runs it on the fake Photoshop.

`node test/live/m4-live-check.js --out <dir> --price-only` writes the fixture (a 768 x 512 synthetic landscape with a red ball) and prices each route without spending: Edit (GPT Image 2.5 Flare, the ball as an elliptical selection), Expand by the mask, position and exact-size routes, Upscale 2x, Remove BG, and Trained > Edit on the image and strength route and the reference route. Without `--price-only` it spends one take per route, copies the before and after composites, the take and the mask to `<dir>`, writes `m4-live-check.log` (versions, then per route the model, settings, price, notes, check results and badges) and, with ImageMagick's `montage` installed, contact sheets of each take beside its mask and the check result. `--routes edit,upscale` runs a subset. Photoshop must be running with the development build installed and signed in; the script never starts, focuses or quits it.

*Verified live* on 27.11 with 0.4.1: the eight routes above (the second reference-route LoRA left out) each placed one take, and the log and contact sheets record the checks. The first run, on 0.4.0, sent blank captures: two findings on real Photoshop that the fake now models. Image data from `imaging.getPixels` must be read (width, height, components) before `dispose()`, after which they are error objects; and with `targetSize`, `sourceBounds` come back in the pyramid level's pixels (`level` n: document pixels divided by 2^n). `host.js` reads both correctly, refuses pixels it cannot read, and the checks throw (noted as "The checks did not run") rather than give a badge on them. The script fails a route whose capture is blank.

## Run the restart checks live (development)

`node test/live/m5-live-check.js --out <dir> [--spend-log <file>] [--cases restart-upload,...]` runs SPEC 12.2 item 9 on a live Photoshop: for each of six cases it writes a `restart` request for the live entry, which saves a document of its own as `dev-live/<case>/<case>.psd`, arms the case's test hook, generates, and once the hook is reached closes its document. The script then quits Photoshop with AppleScript, reads the job record on disk, starts Photoshop again with `open -g` (in the background), waits for `plugin <version> (dev) starting` and the ledger read in `scenario-link.log`, and writes a `check` request: the live entry reports what recovery made of the job, resolves an Unknown job and links its one exact match, waits for the result, tries **Place** while the document is closed, reopens the saved document, checks nothing landed by itself, places, and closes the document. The cases: during upload (Remove BG, 851 Labs, nothing sent), while sending (the paid answer held; 851 Labs), while awaiting approval (a price change after upload; nothing sent), while generating (Edit, GPT Image 2.5 Flare at low quality, held after a status read), while downloading (851 Labs, held with a `.part` file on disk), and while placing (Edit, Flare, held with the record at `applying`). It writes `m5-live-check.log` with the versions and, per case, the states before the quit, on disk, after recovery and at each step, and the boot log lines. It refuses to quit Photoshop while any document is open, so run it with none open. macOS only.

## Panel UI

The panel follows Photoshop's own panels (Properties, Generative Fill, Libraries) and the approved prototype of the creation flows (FLOWS v2). Structure: SPEC section 3 and [docs/spec/wireframes.md](docs/spec/wireframes.md) sections 2, 3, 7 and 8.

**Conventions**
- Colors come from the host theme variables (`var(--uxp-host-background-color)`, `--uxp-host-text-color`, `--uxp-host-text-color-secondary`, `--uxp-host-border-color`, `--uxp-host-widget-hover-background-color`), so the panel follows the four Photoshop brightness themes. The only fixed colors are Spectrum's blue, green and orange for states and accents (agent dot, Jobs badge, kept take, warnings) and a translucent black behind pictures, which reads on light and dark themes.
- 12 px text, 11 px notes, 13 px for the action button and the context title, an 8 px spacing grid. The creation view (`#view-main`) uses plain elements for its controls: action chips, composer chips, menus, popovers, the action button and the confirm and agent cards are `div`s styled in `styles.css` and wired in `ui/create-view.js` by `data-*` attributes (`data-act`, `data-pop`, `data-pick`, `data-pin`, `data-take`, `data-btn`, `data-ref`, `data-dref`, `data-recent`). Reasons, measured on 27.11: `sp-picker` does not show its chosen value, `sp-action-button` with an icon and a label stacks them, and Spectrum widgets do not wrap in a chip row. The prompt stays an `sp-textarea` (native text editing, paste, IME). The other views (sign-in, picker, Jobs, Projects, Settings) keep Spectrum widgets at `size="s"`.
- Menus and popovers (More, a chip's menu, Advanced, Add reference, the agent popover) are absolute boxes inside `.app` (position: relative) above a transparent `#pop-scrim` that closes them on a click outside; one is open at a time, and it opens on the side of its chip with more room (above the composer's chips, as a rule). Pictures (context card, tiles, Recent, chip thumbnails) are `img.cov` with `object-fit: cover` in a fixed box.
- The composer is the last child of the flex column, under `#sc-body`, which holds the top (`.sc-top`: context card and chips) and the middle part (`.sc-mid`). Normally only `.sc-mid` scrolls, so the composer stays pinned without `position: sticky`. Below 600 px of panel height (`@media (max-height: 599px)`), `#sc-body` scrolls as one block and `.sc-mid` takes its natural height, so at the 420 px docked minimum the button stays visible instead of the composer being cut. *Verified live* on 27.11: at the 420 px docked height `#sc-body` scrolls (a 16 px scrollbar beside the context card) and the button stays visible; the test DOM does not evaluate media queries. Under 300 px of width, `.cc-model .v` is capped at 100 px with an ellipsis, so the composer chips keep to two rows at 280 px. Composer chips carry `cc cc-<kind>` classes for these rules. The header's **Jobs** opens a short popover (the six newest jobs, as the prototype draws it); a row or **All jobs** opens the full Jobs view, where the rows carry their action buttons (`jobs-view.js` with `popover: true` leaves the header button to `create-view.js`).
- UXP draws an `sp-textarea` above every other element, and some text of the refs row was drawn through popovers too (*verified live* on 27.11). While a popover is open, `cover()` in `create-view.js` hides the prompt and shows `#prompt-ghost`, a plain div of the same height with the prompt's text, and `.composer.covered` makes the refs row's text transparent; a popover that opens upward stops under the header. Menu rows carry `flex-shrink: 0` (`.pop > *`): in a scrolling flex column UXP shrank them into each other. The context title is one line with an ellipsis (`white-space: nowrap` on the block, the full title as `title`).
- Icons are inline SVG drawn in `plugin/src/ui/icons.js` (outline, 18 px box, `currentColor`); markup asks for one with `data-icon="<name>"` and `icons.fill` draws it. No image files, no icon font.
- The header is one 36 px row that never wraps: the mark, the project (ellipsis, full name in the tooltip), the agent icon with its dot and client name, and **Jobs** with a count (blue while one runs, amber when one waits for the person). Settings, Diagnostics, Help, About and Sign Out are in the panel menu (`plugin/src/ui/menu.js`, declared in `entrypoints.setup`).
- A main view leads with controls; explanations go in tooltips (`title`), in an empty state or under a Details disclosure. Main views never mention ports, the helper, or "later" builds; `test/unit/panel-layout.test.js` checks the markup and every text table, and `test/unit/creation-panel.test.js` runs flows F1 to F5 through the real host on the fake Photoshop.
- The controller (`panel/controller.js`) owns every decision: the context (none, layer, cutout, selection, takes, read again from the active document, layer and selection on Photoshop's notifications, coalesced over 80 ms so the card follows within 200 ms: `host.onDocumentEvents`), the action, its chips and price, the run and the Takes card. `ui/create-view.js` only draws the model the controller emits and reports clicks back. Only actions that run in this build appear: no chip, menu entry or price for a P2 flow.
- Where `sp-picker` is still used (the picker's tag menu), its options are an `sp-menu slot="options"` of `sp-menu-item`s, the chosen one marked `selected` (UXP ignores a value set from code).
- Text that must end with an ellipsis is a block `span` inside the button; UXP does not apply `text-overflow` to a button's own label.

**What UXP 9.4 lays out** (Photoshop 27.11, measured with the probe plugin and the panel's own metrics, *verified live*): flexbox with `flex-wrap: nowrap`, a scrolling middle part (`flex: 1 1 auto; min-height: 0; overflow-y: auto`), `max-width` media queries, `text-overflow: ellipsis` on block elements, `position: absolute` inside a relative box. Images load from `https:` (the model thumbnails, with the domain in the manifest), `data:`, `blob:` and `plugin-data:/<path>`; `file://` and `plugin-data://` do not load. Not supported: CSS grid, `gap`, `position: sticky`, `aspect-ratio`, `window.matchMedia`. A hidden element keeps its last box in `getBoundingClientRect`, so measure only what is shown. The stylesheet test refuses grid, gap, sticky and aspect-ratio.

**Looking at the panel** (development builds, macOS). The panel's UI loop (`plugin/src/dev/ui-loop.js`) reads commands from the data folder, so the look can change without restarting Photoshop:

```sh
node test/live/ui-dev.js push                         # build, copy into the installed plugin, reload the panel
node test/live/ui-dev.js view '{"name":"settings"}'   # main (with "action"), picker, jobs, projects, settings, signin
node test/live/ui-dev.js width '{"px":280}'           # constrain the root to check a width; '{}' removes it
node test/live/ui-dev.js metrics                      # boxes, scroll sizes and texts of every shown element
node test/live/ui-dev.js demo '{"what":"failure"}'    # sample states: jobs, failure, project, adding
node test/live/ui-dev.js capture panel-window.png     # silent capture of Photoshop's main window
node test/live/ui-dev.js makedoc '{"document":{"width":768,"height":512,"fixture":"dev-live/fixture.png"}}'   # a document of the loop's own
node test/live/ui-dev.js select '{"document_id":12,"selection":{"left":200,"top":150,"width":400,"height":300}}'
node test/live/ui-dev.js click '{"attr":"data-act","value":"replace"}'   # or '{"el":"go"}' for an element id
node test/live/ui-dev.js prompt '{"text":"a red boat"}'
node test/live/ui-dev.js pop '{"kind":"more"}'      # '{"close":true}' closes it
node test/live/ui-dev.js state                        # the controller's state and view model
node test/live/ui-dev.js layer '{"document_id":12,"layer_id":3}'   # make a layer active, as a click in the Layers panel
node test/live/ui-dev.js selection '{"document_id":12}'  # the selection's bounds
node test/live/ui-dev.js inspect                      # layers, masks, History and XMP of the loop's document
node test/live/ui-dev.js adopt '{"document_id":13}'   # a document a run of the loop opened (Create image, Upscale)
node test/live/ui-dev.js closedoc '{"all":true}'      # closes the loop's documents without saving
```

The loop keeps the list of documents it made in `dev-ui-made.json` in the data folder, so a `push` (which reloads the panel) never strands one; after a reload, `view '{"name":"main"}'` activates the creation view again (a reload does not call the panel's `show`). The panel docks at 280 px wide; for 320 and 360 px, `width '{"px":360,"shift":80}'` widens the root and shifts it, and the captures are stitched. Before `makedoc`, check the startup disk's free space: on a nearly full disk Photoshop opens a modal "Scratch Disk Low" dialog that blocks the loop and every AppleEvent until a person dismisses it (seen on 27.11 with about 20 GB free); an agent may not click it.

`demo` draws sample states of the account views and Jobs rows with the panel's own render code; it spends nothing and touches no document, and its pictures are never shown in the creation view. The panel does not hear the notifications of its own commands: after `select` or `layer`, send `view '{"name":"main"}'` so it reads the document again. `makedoc`, `select`, `layer`, `selection`, `inspect`, `composite` and `closedoc` act only on documents the loop made (through the development live entry) or adopted (a new document opened by a run the loop started after it started) and refuse any other; `click` on `#go` spends the price on the button. `capture` finds Photoshop's main window with Quartz (through `uv`) and runs `screencapture -x -o -l <window id>`, which neither activates Photoshop nor makes a sound; crop the panel from the result with ImageMagick. Photoshop hides docked panels while its Home screen shows (no document open), so a capture needs an open document; `metrics` works either way. Release builds replace the loop and the demos with stubs (`test/unit/bundle.test.js`).

## Connecting a real client by hand

```sh
pbpaste | node helper/bin/scenario-photoshop.js setup <claude-code|codex|cursor|claude-desktop> --local --token-stdin
node helper/bin/scenario-photoshop.js setup cursor --dry-run --local   # shows what it would do
```

`--local` points the client at this checkout instead of the npm package. The helper reads `SCENARIO_PHOTOSHOP_TOKEN` when the client sets it, else the token file that setup wrote.
